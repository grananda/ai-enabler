AI for IT · SWAT framework

Working with AI, as a team

A manual for team leads: what is standard, what you adapt, and what we build together with you.

Read this first

Five minutes that save you six weeks.

  • You own this. AI adoption is not a tool rollout that arrives finished. It lands in your repository, your review process, your definition of done.
  • Three kinds of work are kept separate on purpose: what you follow, what you adapt, and what we build with you. Mixing them is what stalls teams; the next slide shows why.
  • Nothing here is a side project. Every step is done on a real ticket, in a real repo.

Realistic pace: 2 weeks to the floor, 6 weeks to a working shared setup, 12 weeks to AI having a defined place in your delivery flow. Teams that try to do it in two weeks get a demo, not a practice.

Gate · you do this

Prerequisites: the floor

Honest framing: none of this is AI-specific. All of it blocks AI.

  • One shared repository per product, with write access for the whole team, not one engineer's fork.
  • Named owners for the repo, the pipeline and the documentation. A name, not a team alias.
  • One known place where team documentation lives, preferably a docs folder in the repository, and it is current enough to trust.
  • An onboarding path a new joiner can follow alone and reach a first merged change in two days.
  • Licences and access granted. See the next slide.
  • A four-number baseline, taken from tools you already have: cycle time, review waiting time, pull request size, rework or reverts.

Why it is a gate: AI amplifies what is written down. With no shared repo, no owners and no docs, it amplifies nothing, and every engineer re-explains the same system to the same assistant, privately, forever.

Gate · you request, organisation delivers

Access & licence checklist

Ask once, as a team. Not per person, not per sprint.

  • Assistant licences for every engineer, not a pilot subset. Split teams produce split practice.
  • Approved models and endpoints: which models, which endpoint and data region, and which data may go into a prompt.
  • Repository access for the assistant: read, plus permission to open pull requests.
  • MCP connections you actually use: issue tracker, wiki, CI, observability. List yours by name.
  • A sanctioned source for skills and plugins: the internal marketplace, not random downloads.
  • A named approver and an SLA for each of the above.

If a request sits longer than two weeks, escalate it to the SWAT team. Do not build a workaround; workarounds become the setup nobody can support.

Layer 1

The standards

Six rules. Same for every team, whatever you build.

  1. Context lives with the code: instruction files in the repo, reviewed in pull requests.
  2. Skills, agents and plugins have a name, an owner and a version, so they outlive their author.
  3. AI-assisted output passes a defined review gate, with a human who is accountable for it.
  4. AI's place in the delivery flow is written down: one page, per team.
  5. Tests are the contract: derived from testable acceptance criteria, never from generated code.
  6. Known issues are logged, not remembered, and reviewed every sprint.

One slide each, next. Nothing in this list depends on your stack, your repo layout or your deployment model. That is exactly why these are the standards.

Layer 1 · Standard 1

Context lives with the code

Instructions for the assistant are source code. Treat them that way.

repo/
  CLAUDE.md            how this repo works: build, test, conventions, constraints
  .claude/
    skills/            your team's repeatable procedures
    agents/            specialist reviewers
    settings.json      permissions and tool access
  docs/adr/            decisions and the reasoning: why, not just what

The rules

  • In the repo, in version control, changed by pull request. Never in a personal notes app, never only in the wiki.
  • One file at the repo root. In a monorepo, one more per application or library, and only where that module genuinely differs.
  • Written for an agent, not for a human reader. Concrete commands, real paths, hard constraints. No mission statements.
  • Stale context is worse than no context. A change to the build or a convention updates the file in the same pull request.
  • Keep the root file to about a page. Link out for the rest; an agent that reads everything learns nothing.
Layer 1 · Standard 2

Skills, agents and plugins

Start from the marketplace. Do not rewrite what already exists.

The starter set most software teams need

  • Explain this codebase / onboard to a repo
  • Test-first implementation
  • Pull request review agent: comments first, a human always reviews
  • Pull request description and changelog
  • Debugging and incident triage
  • Dependency upgrades and migrations
  • Spec → plan → build, for changes too big for one sitting

Write your own only when the procedure is specific to your product and you have done it by hand at least three times. Anything else is a marketplace item you have not found yet.

Layer 1 · Standard 2 (cont.)

Conventions, so assets outlive their author

The failure is predictable: the person who wrote it moves on, nobody dares delete it, nobody trusts it.

  • Name: area first, then what it does: api-add-endpoint, release-prepare. Readable in a list of forty, grouped by area when sorted. Lowercase letters, numbers and hyphens only, and it must match the folder name; the skill does not load otherwise.
  • Own: one named owner under metadata in the frontmatter. No owner means it is deleted at the next review.
  • Version: semantic version under metadata. A breaking change bumps the major and says so.
  • Review: assets live in the repo and change by pull request, like any other code.
  • Prune: quarterly. Unused for 90 days means archived, not kept "just in case".
.claude/skills/api-add-endpoint/SKILL.md
---
name: api-add-endpoint
description: Adds a REST endpoint following this repo's conventions. Use when a ticket asks for a new endpoint.
metadata:
  owner: a.owner
  version: "1.2.0"
---

Ten trusted skills beat forty orphans. A folder nobody trusts is worse than an empty one: it teaches the team to ignore shared tooling.

Layer 1 · Standard 3

The review gate for AI-assisted output

The one rule with no exceptions: a human is accountable for every merged line.

  1. The author declares it. A checkbox in the pull request template. No ceremony, no stigma, no approval workflow.
  2. The author has read every line and can explain why it is there.
  3. Tests exist, and they fail without the change. The author saw them fail before the change was written, and ticks that in the template too.
  4. No new dependency, schema change, public API change or secret handling without explicit human design first.
  5. The reviewer reviews the code, not the prompt. How it was produced does not change the bar.

Cap the size. AI makes a 2,000-line pull request easy to produce and impossible to review. Split it to what a reviewer can actually hold in their head. Size is about readability; the total load is handled on the next page.
Escalate by risk, not by size: security-sensitive, data-model and public-contract changes go to a named reviewer, not to whoever is free.

Layer 1 · Standard 3 (cont.)

Keep review within capacity

AI writes code faster than people can review it. Smaller pull requests make each review easier; they do not reduce the total a team must review.

  1. Machines before humans. A pull request reaches a human only when build, tests and static analysis are green. People never spend time checking what a machine can.
  2. A limit on open pull requests. The team agrees a maximum. At the limit, nobody starts new work: review or finish first. Produce only as fast as you can review.
  3. Risk paths have named reviewers. Sensitive folders, such as authentication, payments, migrations and public interfaces, are listed in a code-owners file, so changes there go to the named expert automatically.
  4. Judgement moves upstream. For non-trivial work the tests are approved before the code is written (Standard 5), so the diff review checks the code matches what was agreed.

Review is now the constraint. A permanent reviewer only moves the queue. What shrinks it is less to read: machines check first, people agree the tests first, and new work waits for review to catch up.

Layer 1 · Standard 4

Where AI enters the delivery flow

Intake→Shape→Build→Review→Ship→Operate
  • Intake: AI drafts and enriches tickets. A human decides what enters the backlog. No autonomously created work.
  • Shape: AI drafts the spec and the plan. The team owns the acceptance criteria.
  • Build: AI writes code and tests. An engineer drives, and stops it when it drifts.
  • Review: AI takes the first pass on mechanics. Humans judge intent, design and risk, and have the final word.
  • Ship: AI drafts release notes. The pipeline itself does not change.
  • Operate: AI triages logs and helps with incidents. It takes no autonomous action in production.

Write your own one-page version of this slide, with your stage names. It is the single most useful artifact your team will produce in the first 12 weeks. It turns "we use AI" into something a new joiner can follow.

Layer 1 · Standard 5

Tests are the contract

This is where AI-assisted teams quietly lose quality. On this page, "spec" means the ticket's acceptance criteria, not the full spec-driven development described later.

  • Stories carry acceptance criteria clear enough to write tests from, before any code. Vague criteria produce output that is plausible and wrong, and plausible is far more expensive than broken. Agree this with your product owner early: it is a habit the team builds during the transformation, not one it is expected to have on day one.
  • Test first for anything non-trivial. Red, green, refactor. The assistant is very good at this loop.
  • A test the assistant wrote to pass its own code is not evidence. Derive tests from the acceptance criteria first: the assistant may draft them, the engineer checks each one against a criterion, then the implementation is generated against them.
  • Review the tests before the code. For non-trivial work, the tests are approved before implementation starts; the diff review then only checks the code matches them.
  • Coverage is not the goal. Failing on the right thing is.
  • Never let a test be weakened to make a build pass. Watch for it explicitly in review; it is the most common silent regression.
Layer 1 · Standard 6

Log known issues

A file in the repo or a board column. Anything except memory.

DateWhat happenedWhere / triggerImpactWorkaroundOwnerStatus

21 SepIssue-tracker connection times out after ~10 minMCP, ticket lookupBlocks the triage skillReconnect manuallyA. OwnerSent to SWAT

Log these four things

  • An area where the assistant is confidently wrong, so it can be fixed in the context files.
  • A tool or connection that fails in a repeatable way, so it can be fixed centrally.
  • A skill that misfired or drifted, so its owner can fix or retire it.
  • A defect caused by AI-assisted code, linked to its pull request, so the pattern is visible and the context or checks can be fixed.

Ten minutes per sprint. Unlogged pain is pain that every other team will feel again, and it is the raw material the SWAT team uses to improve the standards.

Layer 2

Templates you will be given

Starting points, not prescriptions. Adapt the content; keep the intent.

  • Context file template, one variant per stack: Angular, Spring, Quarkus, Next.js, monorepo
  • Pull request template carrying the AI declaration, the review gate and the spec-updated check
  • Workflow one-pager: "where AI enters our flow"
  • Known-issues log
  • Skill and agent frontmatter: name and description, owner and version under metadata
  • Access and licence request pack
  • New-joiner onboarding path, AI-aware
  • Quarterly pruning checklist

Also provided

  • Hook templates for rules that must always run, per stack: lint after every edit, tests before a commit. Context files advise; hooks enforce.
  • Stacked pull request how-to: a big change as a sequence of small, reviewable steps.
  • Property, mutation and contract test templates, for high-risk modules only, and later.

If you delete a section of a template, write one line in your repo docs saying why. That line is how the SWAT team learns which parts of the framework do not survive contact with real teams.

Layer 3

What the SWAT team builds with you

Only your team knows your repo layout, build system, integrations, permissions and deployment model. So this is a working session, not a hand-over.

In the session

  • Map your repositories and decide where context files go
  • Wire the MCP connections your team actually uses
  • Tailor the starter skill set to your stack
  • Fit the review gate into your existing pipeline and code owners, including named reviewers for risk paths
  • Set up the language server, so the agent navigates code precisely instead of searching text
  • Tune the AI first-pass reviewer to your conventions; it is never the agent that wrote the code
  • Take one real ticket and run it end to end, together

Come prepared with

  • A 15-minute walkthrough of your main repository
  • Your pipeline, as it is, not as it should be
  • One representative ticket, already refined
  • Your top three frustrations from the last sprint

Later, when the baseline shows the need: code health tracking, a spec and plan review pilot, auto-approval of low-risk pull requests.

The output is committed code: context files, skills and templates merged into your repo. Not slides, not a report.

Spec-driven development: the direction, not the start

Four rungs. Skipping rungs is the most expensive mistake on this page. Rungs are shorthand for the Engineering Practices dimension of the AI-DLC maturity matrix, not a separate scale.

1
Assisted edits: individual use, in the editor, nothing shared.≈ Maturity L2 Where most teams are today. Real gains, but they leave with the person.
2
Shared setup: context files in the repo, agreed skills, a review gate.≈ Maturity L3 The target for this quarter. This is where team-level gains start.
3
Workflow integration: AI has a written place from intake to operate.≈ Maturity L3–L4 Next quarter.
4
Spec-driven development: specs and plans are the source of truth; tests come from acceptance criteria; code is generated against them.≈ Maturity L5 The direction of travel.

Do not start at rung 4. Teams that skip 2 and 3 produce beautiful specifications nobody maintains, and deliver exactly as before.
You are ready for rung 4 when your specs and acceptance criteria are kept current without anyone chasing it. A checkable sign: most pull requests that changed behaviour last month also touched the spec. Rung 4 itself is when changes start from the spec.

Keeping specs current, in practice

A habit, not an automation. Four mechanisms, usually adopted in this order.

  1. The spec lives in the repo, next to the code, so both change in the same pull request.
  2. A team rule, carried in the pull request template: a change in behaviour also updates the spec, and reviewers reject it otherwise. One checkbox: "spec updated, or not affected".
  3. The context file tells the agent to do it. The assistant edits the spec as part of the task; the engineer checks the edit in review.
  4. Spec-driven tooling makes it the only path, for example OpenSpec or Spec Kit: a change starts as a proposed spec update, the agent plans and implements against it, and on merge the update becomes part of the living spec.
# CLAUDE.md, excerpt
## Specs
- Specs live in docs/specs/, one file per capability.
- Any task that changes behaviour updates the matching spec in the same change.
- If no spec covers the behaviour, stop and ask before creating one.

Direction matters. At rungs 2 and 3 the spec follows the code: documentation keeping up. At rung 4 the code follows the spec.

Who does what

Team lead (you)

Own the outcome. Unblock licences and access. Protect the review gate when the sprint is late. Send honest feedback to SWAT.

AI Ambassador: one named engineer

Roughly 20% of their time. Owns the context files and the team's skills. Runs the known-issues review. Not a side duty for whoever is enthusiastic this month.

Every engineer

Reads the context files. Declares AI-assisted work. Logs known issues. Fixes the context file instead of re-prompting around it.

SWAT team

Owns the standards, the templates and central tooling. Escalates organisational blockers. Runs the implementation sessions.

What SWAT does not do: decide your repo structure, own your context files, or act as your reviewer. Consistency at the methodology level, never a one-size-fits-all technical setup.

How you know it is working

Trust these signals

  • A new joiner reaches their first merged change faster than the last one did
  • Review comments move from "what does this do" to "is this the right design"
  • The context files are edited by more than one person
  • The known-issues log has entries, and they get closed
  • Private prompt tricks are replaced by shared skills

Context, never targets

  • Lines of AI-generated code
  • Assistant usage or session counts
  • Percentage of pull requests "touched by AI"
  • Number of skills in the folder

They measure activity, which is useful to see whether adoption is happening. None of them measures delivery, and teams optimise whatever becomes a target.

Failure modes, in order of likelihood

  • Tools without practice change: licences are bought, everyone is enthusiastic, nothing about delivery changes.
  • Context files written once: six months later the agent is confidently describing a system that no longer exists.
  • The review gate skipped for "small" changes: the first AI-related incident is often a one-liner.
  • Forty skills, one author, no owners: the team learns to distrust shared tooling.
  • Starting with spec-driven development: elegant specs, unchanged delivery.
  • Every team solving the same problem privately: nothing logged, nothing shared, the same 20 minutes lost in every team.

Your checklist

All of this should be true 12 weeks from your first session.

  • Prerequisites met; licences and access granted
  • AI Ambassador named, with time protected
  • Context file at the root of every active repo, changed by pull request
  • Starter skills installed; every team addition has an owner and a version
  • Pull request template carries the AI declaration and the review gate
  • Open pull request limit agreed; checks green before any human review
  • Workflow one-pager written, and followed
  • Tests derived from acceptance criteria, not from generated code
  • Known-issues log live and reviewed each sprint
  • One real feature delivered end to end with the SWAT team
  • Honest 12-week review done, and needs sent back to SWAT

Stuck on any line? That is what the SWAT team is for. Bring the blocker, the repo and one real ticket.
